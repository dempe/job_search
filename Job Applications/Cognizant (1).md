> You have experience with Spring Boot. It uses a lot of annotations -- @Autowired, @Required, and so on. What is the purpose of those annotations, what do they do internally, and how does the application come up?

```
The annotations are how you tell Spring what to manage and how to wire it together.

On startup, @SpringBootApplication triggers a component scan of the package tree. Anything marked @Component, @Service, @Repository, or @Controller gets registered as a bean definition in the application context. @Configuration classes contribute beans explicitly through @Bean methods. Auto-configuration then reads what's on the classpath and the conditional annotations to supply sensible defaults, like an embedded Tomcat and a DataSource.

Spring instantiates those beans in dependency order and injects the dependencies. @Autowired marks an injection point; it resolves by type first, then by qualifier or name if the type is ambiguous. @Value pulls in configuration properties.

Internally, a lot of this is proxying: @Transactional and @Cacheable work because Spring wraps the bean in a proxy that applies the behavior around your method. That's why calling an annotated method from inside the same class skips it -- the call never goes through the proxy.

One thing I'd add: field-level @Autowired has fallen out of favor. Constructor injection is preferred, because dependencies are explicit, the object is immutable once built, and it's testable without a container.
```

> If I have five or six microservices, and service A needs information from B, C, and D -- say a customer service that needs orders and payment details -- what communication mechanism would you use, and what security would you put in place?

```
For a request where the caller needs an answer right now, synchronous REST over HTTPS, with the aggregating service calling the others and assembling the response. I'd make those calls in parallel rather than in sequence, give each a timeout, and put a circuit breaker around them so one slow dependency can't take down the aggregate. If the data is read-heavy and tolerates staleness, I'd cache it.

For anything that doesn't need an immediate answer -- order placed, payment captured -- events over Kafka, so the producer doesn't care who consumes them and services stay decoupled.

For security: TLS between services, and service-to-service authentication rather than trusting the network. That usually means OAuth2 client credentials or mTLS, with a short-lived token carrying scopes, and each service enforcing its own authorization rather than assuming the gateway did it. The gateway handles authenticating the end user and rate limiting, and the user's identity propagates as a signed token so the downstream services can make their own decisions. Plus a correlation ID on every request, so you can trace a single user action across all of them.
```

> Besides RestTemplate, what other options does Spring Boot give you for calling a REST API from one microservice to another?

```
RestTemplate is the old blocking client and is in maintenance mode now. The current options are:

- WebClient, from WebFlux -- non-blocking and reactive, and the recommended replacement. It works fine in a blocking app too if you call block().
- RestClient, added in Spring 6.1 -- a fluent, synchronous client, the natural drop-in for RestTemplate.
- Declarative HTTP interfaces -- you define a Java interface with @GetExchange or @PostExchange and Spring generates the implementation.
- Spring Cloud OpenFeign -- the same declarative idea, popular where service discovery and load balancing are already in play.

Under the hood they all sit on a client library like Apache HttpClient, OkHttp, or the JDK's own HttpClient.
```

> If I'm using a Kafka topic for communication between microservices, what do I have to do as a producer and as a consumer to post a message to a topic and consume from it?

```
As a producer: pick the topic and a partition key, since the key decides which partition a message lands in and therefore what ordering guarantee you get -- ordering holds per partition, not per topic. Choose a serializer, ideally with a schema registry so producers and consumers agree on the format instead of trading raw bytes. Then decide your durability settings: acks=all with replication if you can't lose messages, retries plus enable.idempotence=true so a retry doesn't produce a duplicate.

As a consumer: join a consumer group, which is what gives you parallelism -- partitions are distributed across the consumers in the group, so you never get more parallelism than partitions. Deserialize with the same schema. Then decide how you commit offsets: auto-commit is easy but can lose or double-process messages around a crash, so I prefer committing manually after the work is done, which gives at-least-once delivery. That means the consumer's handling needs to be idempotent.

Partition count is worth thinking about up front. Adding partitions later changes how keys map to partitions, which breaks the ordering guarantee for existing keys.
```

> What issues have you faced as a consumer, in UAT or in production, and how did you handle them?

```
The most common is a bad message: malformed, incomplete, or a schema the consumer doesn't understand. Left alone, it's a poison pill -- the consumer retries forever and the partition stops moving. The fix is a dead-letter queue: after N attempts, the message goes to a DLQ topic with the error attached, the consumer moves on, and someone looks at the DLQ afterwards. That's what I built into the pipeline at Octimine, and it's the main reason one bad document stopped being able to halt an entire run.

Second is duplicates. At-least-once delivery means the same message can arrive twice, so the handler has to be idempotent -- either a natural upsert keyed on the message key, or a processed-id table.

Third is rebalancing. A consumer that takes too long between polls gets kicked from the group, which triggers a rebalance, which makes it slower still. The fix is tuning max.poll.records and max.poll.interval.ms, or moving the slow work off the poll thread.

Fourth is schema evolution: a producer adds a field and old consumers break. A schema registry with compatibility rules prevents that.
```

> You're seeing consumer lag on a topic in the portal, and messages are piling up. What would you do to reduce the lag?

```
First, find out whether it's a spike or a trend, and whether the lag is on all partitions or just a few. Uneven lag usually means a hot key -- one partition is getting a disproportionate share of the traffic -- which is a partitioning problem, not a capacity problem.

If it's even, work out whether the consumer is slow or there just isn't enough of it. I'd look at processing time per message and where it goes: a downstream call, a database write, a lock. The cheapest win is usually batching those writes or calls rather than doing them one message at a time.

To add capacity, add consumers to the group -- up to the number of partitions, since that's the ceiling. Past that, you add partitions, keeping in mind that changes key-to-partition mapping.

If the producer rate has genuinely outgrown the consumer, those are the levers: more partitions, more consumers, faster handling. And I'd want an alert on lag so this gets caught before someone notices it in a dashboard.
```

> Which Java version have you worked with, and what are the main features of Java 17 compared to previous versions?

Most recently 17, and 11 before that.

> Do you have hands-on experience with the streams concept?

```
Yes. A stream is a pipeline over a collection: you build up intermediate operations like filter, map, and sorted, and nothing runs until a terminal operation like collect, reduce, or forEach pulls values through it. That laziness means it can fuse the operations into a single pass.

The practical appeal is that it's declarative -- you say what you want rather than writing the loop -- and it handles grouping and partitioning cleanly through Collectors. It also parallelizes with one call, though in practice that's only worth it for large, CPU-bound work on a source that splits well.
```

> Using streams, given the numbers 10, 11, 21, 31, 41, pick out the numbers that start with 1.

```
List<Integer> numbers = List.of(10, 11, 21, 31, 41);

List<Integer> startingWithOne = numbers.stream()
        .filter(n -> String.valueOf(n).startsWith("1"))
        .toList();

// [10, 11]
```

> Same idea with a string: for "Christopher", tell me how many occurrences of each character there are.

```
Map<Character, Long> counts = "Christopher".chars()
        .mapToObj(c -> (char) c)
        .collect(Collectors.groupingBy(Function.identity(), Collectors.counting()));

// {r=2, h=2, s=1, t=1, C=1, e=1, i=1, o=1, p=1}
```

- Use `LinkedHashMap::new` as the map factory in `groupingBy` if the output needs to keep first-appearance order.
- `Collectors.counting()` returns `Long`; use `summingInt(c -> 1)` if an `Integer` is wanted.
