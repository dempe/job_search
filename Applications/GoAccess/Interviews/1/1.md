```
One thing to clear up first: with the App Store, Apple does the charging, so the risk isn't double-charging. It's the entitlement being wrong -- a paying customer locked out, or content unlocked without a real purchase.

The failures I designed against:

1. Duplicate deliveries. Apple retries server notifications until it gets a 200, and the app can also send the same transaction from the device. So the same event can arrive more than once.
2. Out-of-order events. A purchase and a refund can arrive in either order.
3. Partial failures. A Lambda that times out after writing but before responding, or Apple's API being briefly unavailable.
4. Forged payloads. Anyone can POST to a public endpoint.

For forgery, I validate Apple's signed JWS before trusting anything -- the full x5c certificate chain from the leaf through the intermediates to Apple's root.

For duplicates and retries, every write is idempotent. I key on Apple's transaction ID (and the notification UUID for notifications) and use DynamoDB conditional writes, so processing the same event twice is a no-op instead of a second state change.

For ordering, I don't apply events as deltas. The entitlement is derived from the latest signed transaction state, compared by Apple's signed date, so an older event arriving late can't overwrite a newer one.

For partial failures, the API Gateway handler just verifies and enqueues to SQS, then returns. The processing happens asynchronously with retries, and anything that keeps failing lands in a dead-letter queue with a CloudWatch alarm. Since processing is idempotent, retrying or replaying from the DLQ is always safe.
```

Apple is the source of truth, so when my state might be wrong, I don't guess -- I ask Apple. For a transaction in doubt, I query the App Store Server API for that customer's transaction history and recompute the entitlement from it. The app's restore-purchases flow triggers the same path from the device.

I also separate transient failures from permanent ones. Things like timeouts and rate limiting retry automatically with backoff. Permanent ones -- an invalid signature, a malformed payload -- go straight to the dead-letter queue with the error attached, and the alarm fires.

```
Ingestion: patent data landed in our data warehouse, and new and updated records were published into a Kafka topic as they arrived. Everything was keyed by patent ID. That matters, because Kafka Streams can only join and group locally when related records are on the same partition, so keying consistently up front is what makes everything downstream work.

Joins: a patent didn't arrive all at once. We'd get the metadata -- authors, dates, classifications -- and later the full text, as separate messages that could be days apart. I modeled the latest state of each part as a KTable and joined them on patent ID. When either side updated, the join re-emitted the combined record.

Grouping and windowing: each analytic grouped by key and aggregated into a state store. The time-based analytics used windowed aggregations, so we computed over a bounded window of recent records instead of the whole history.

Compaction: the KTables and state store changelogs were backed by compacted topics, so Kafka keeps only the latest value per key. That keeps storage bounded and makes rebuilding state fast.

Sink: the final topic fed Elasticsearch, which backed the API and the customer dashboard. Writes were upserts by document ID, so reprocessing a record just overwrote it with the same result.

Failure handling: this was the main reason for the migration. In the batch job, one bad document could kill the whole run. In the pipeline, records that failed to deserialize or process went to a dead-letter topic with the error attached, and everything else kept flowing.

Recovery: state stores are restored automatically from their changelog topics when an instance restarts or a partition moves, and committed offsets mean we pick up where we left off. Since the sink was idempotent, we could fix a bug and replay from the DLQ, or reset the application and reprocess from scratch, without corrupting anything. Every analytic had unit tests run in CI, so we could change analytics without risking bad data.
```
